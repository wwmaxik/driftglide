## Как внести свой вклад?

### Сообщения об ошибках (Bug Reports)

Перед созданием нового issue, пожалуйста, проверьте уже открытые и закрытые задачи — возможно, проблема уже известна.

При оформлении issue укажите:
- Чёткий и понятный заголовок.
- Шаги для воспроизведения проблемы.
- Ожидаемое и фактическое поведение.
- Используемый Wayland-композитор (driftwm, Sway, Hyprland и т.д.).
- Логи выполнения (запустите с `RUST_LOG=driftglide=debug driftglide`).

### Предложения новых возможностей (Feature Requests)

При создании запроса на новую функцию:
- Объясните мотивацию и решаемую задачу.
- Опишите предлагаемую реализацию или поведение интерфейса.
- Учитывайте влияние на производительность и рендеринг.

### Pull Requests

1. **Форкните репозиторий** и создайте новую ветку от `main`.
2. Убедитесь, что проект собирается без ошибок и предупреждений:
   ```bash
   cargo check
   cargo build --release
   ```
3. Проверьте форматирование кода:
   ```bash
   cargo fmt --check 2>/dev/null || true
   cargo clippy 2>/dev/null || true
   ```
4. Проверьте работу изменений в вашей Wayland-сессии.
5. Откройте Pull Request с подробным описанием внесённых изменений.

## Настройка окружения

### Необходимые инструменты:
- **Rust** (версия 1.70 или новее) и `cargo`
- Библиотеки разработки Wayland
- `wl-clipboard` (`wl-copy` и `wl-paste` для работы с буфером обмена)
- Системные шрифты (Noto Sans, DejaVu Sans или Liberation Sans)

### Запуск из исходников:
```bash
cargo run --release
```

Запуск с подробным выводом логов:
```bash
RUST_LOG=driftglide=debug cargo run
```

## Стандарты разработки

- **Идиоматичный Rust**: Пишите надёжный, безопасный код. Используйте `match`, `Option`, `Result`. Избегайте `.unwrap()` на продакшн-путях, которые могут привести к панике.
- **Потокобезопасность**: Защищайте мьютексы от poisoning (`.unwrap_or_else(|e| e.into_inner())`).
- **Эффективный рендеринг**: Избегайте лишних аллокаций в циклах отрисовки. Используйте буферизацию `DoubleBufferedShm` и эффективный рендеринг `tiny-skia`.
- **Дисциплина Wayland-протоколов**: Проверяйте флаг `busy` у SHM-буферов и корректно коммитьте повреждённые области (damage rects).
- **Многоязычные горячие клавиши**: Сочетания клавиш должны работать как в английской, так и в русской (XKB Cyrillic) раскладках.

## Git-процесс и формат коммитов

Мы придерживаемся стандарта Conventional Commits:

```
<тип>(<область>): <краткое описание>
```

Типы:
- `feat`: Новая функциональность
- `fix`: Исправление ошибки
- `docs`: Изменения в документации
- `style`: Форматирование, пробелы и т.д.
- `refactor`: Рефакторинг кода без изменения поведения
- `perf`: Улучшение производительности
- `test`: Добавление или исправление тестов
- `chore`: Сборка, зависимости, служебные файлы
